# Workflows

After reading this guide, you will know:

- How to declare workflow steps and transitions
- How routers subscribe to events and advance cases
- How to keep your Statesman machine aligned with your workflow

## WorkflowDefinition: steps + transitions

Workflows are declared using `Groundwork::CaseManagement::WorkflowDefinition`:

```ruby
PermitWorkflow = Groundwork::CaseManagement::WorkflowDefinition.new do |w|
  w.applicant_step  :submit_application
  w.system_step     :prescreening,       PermitPrescreeningJob
  w.staff_step      :examiner_review,    PermitReviewTask

  w.on_start :submit_application

  w.transition from: :submit_application, on: "PermitApplicationFormSubmitted", to: :prescreening
  w.transition from: :prescreening,       on: "PermitPrescreeningCleared",      to: :examiner_review
  w.transition from: :prescreening,       on: "PermitPrescreeningDenied",       to: :closed
end
```

### Step types

- `applicant_step(name)` — a user action (typically “form submission”)
- `system_step(name, job_class)` — background processing (`ActiveJob`)
- `staff_step(name, task_class)` — staff work queue items (`Groundwork::StaffTask` subclass)
- `third_party_step(name)` — external waiting state (no built-in execution)

### Closing a workflow

Use `to: :closed` to end a workflow. Routers call `case.close!` when a workflow step resolves to `:closed`.

## WorkflowRouter: event-driven process manager

Routers are subclasses of `Groundwork::CaseManagement::WorkflowRouter`:

```ruby
class PermitWorkflowRouter < Groundwork::CaseManagement::WorkflowRouter
  workflow  PermitWorkflow
  case_class PermitCase
end
```

Routers:

- Subscribe to each event name declared by `workflow.event_names`
- On the “start event”, create a case (`build_case`) and advance it
- On all other events, find matching cases via `PermitCase.for_event(payload)` and advance each

### Start event payload requirements

The default `build_case` expects `event.data[:application_form_id]`. If your start event uses a different key, override `build_case(event)`.

### Executing steps

After transitioning, routers execute the next step:

- `system_step` enqueues a job
- `staff_step` creates a task
- `third_party_step` is a no-op by default

See the step classes in `lib/groundwork/case_management/steps/`.

## Keeping Statesman aligned

Your host app owns the Statesman machine class for each case type (generated by `groundwork:case`).

Rule of thumb:

- Every workflow step name should exist as a Statesman state.
- Every workflow transition should exist as a Statesman transition.

If the workflow and machine diverge, the router may compute a next step but the state machine will reject the transition.
